# Experiment Guide

This document is a run-by-run log of the experimental workflow behind the dissertation
*"Agent-Based Modelling of Compute Placement for Latency- and Throughput-Aware Mobile Edge
Computing"*. Where `README.md` documents *what the code is*, this document documents *what was
run, in what order, why, and what each run produced*, so that the pipeline can be followed and
reproduced stage by stage rather than reverse-engineered from the scripts.

All commands are run from `abm_communication_networks/` (the project root). All scripts are
deterministic given a seed (`tests/test_simulation.py` verifies this), so re-running any stage
below regenerates byte-identical CSV logs.

## Two output directories - do not confuse them

- **`output/`** (gitignored, *not* in this repo) - the raw output of every run below: trained
  Q-tables (`models/*.pkl`), per-step CSV logs, and PNG figures. Fully regenerated by re-running
  the pipeline; nothing in it is hand-edited.
- **`results/`** (committed) - two things, both pulled out of `output/`:
  - hand-curated summary CSVs, one folder per Chapter 7 section
    (`Chapter7_ExperimentA_baseline_comparison/`, `..._ExperimentB_latency_efficiency/`,
    `..._ExperimentC_mobility_migration/`, `..._ExperimentD_admission_allocation/`,
    `..._RN_CR_training_convergence/`) - the direct source for the dissertation's tables and
    figures;
  - `Chapter7_complete_data_by_scenario/` - a full, static copy of `output/`'s per-scenario
    contents (models, logs, figures) for the 13 scenario/condition combinations behind the main
    results, pruned of files no analysis script actually reads (see `results/README.txt` for the
    exact layout and what was removed). This is what lets someone inspect or re-derive every
    number in Chapter 7 without re-running Stage 1 first.

## Stage 0 - Environment and sanity check

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m pytest tests/ -v
```

**Why:** before trusting any downstream number, confirm the simulator runs cleanly for 10 steps
and that two runs with the same seed produce identical `hop_counts.csv` (§5.4). This reproducibility
guarantee is what makes the paired-seed design in §6.3.3 valid - if it ever fails, nothing below
this line can be trusted.

**Generates:** nothing persisted; pass/fail only.

## Stage 1 - Main training + evaluation pipeline

```bash
python experiments/generate_results.py --seeds 20
python experiments/generate_results.py --scenarios urban_controlled --seeds 20
```

**Why:** this is the pipeline described in §5.2 and is the dependency root for almost everything
else. For each scenario it (1) trains the RN positioning agent for 1000 steps and freezes it
(§4.4, `train_rn`), (2) trains the CR placement agent against the frozen RN for a scenario-specific
step count (5000 for Urban-Light, 2000 for Urban-Medium, 3000 for Urban-Dense) (`train_cr`), then
(3) evaluates all five placement strategies (No-CR, Random, Static, exhaustive-greedy oracle,
trained RL agent) over `seed = 0..19`, 300 steps each with the first 50 discarded as warm-up
(§6.2.1, §6.3.1).

`--seeds 20` is required explicitly - the script's own default is 5 (the original pilot sample,
§6.3.1), and every number reported in the dissertation uses the quadrupled n = 20 sample.

`urban_controlled` is run as a separate invocation because it is not one of the three main
scenarios (`SCENARIOS_DEFAULT`); it exists purely to isolate mobility from load for Experiment C
(§7.5.2) and is only consumed by `analyze_experiment_C_controlled.py` below.

**Depends on:** Stage 0 only.

**Generates**, under `output/output-<scenario>/`:
- `models/rn_{id}.pkl`, `models/cr_qtable.pkl` - the frozen Q-tables reused by every later stage
- `logs/train_rn/rn_reward.csv` - RN training reward per step → **Table 7.1**
- `logs/train_cr/cr_reward.csv`, `cr_reward_global.csv`, `cr_delta_q.csv` - CR training reward
  and Bellman-update magnitude → **Table 7.2, Figure 7.1-7.2**
- `logs/eval/{trained,no_cr,random,static,exhaustive_greedy}/s{0..19}/satisfaction_summary.csv`,
  `satisfaction_users.csv`, `cr_utilization.csv`, `hop_counts.csv` - per-seed, per-step outcomes;
  the raw material for every Chapter 7 table
- `fig1_training_curves.png` … `fig5_satisfaction_timeseries.png` → **Figures 7.1, 7.2, 7.3, 7.4**

## Stage 2 - Experiment A statistics (§7.2, §7.6)

```bash
python analysis/run_analysis.py --logs-dir output/output-urban_light/logs
python analysis/run_analysis.py --logs-dir output/output-urban_medium/logs
python analysis/run_analysis.py --logs-dir output/output-urban_dense/logs
python analysis/paired_diff_experimentA.py
```

**Why:** `run_analysis.py` re-derives the training-convergence summary (first-20%-vs-last-20%
reward, ΔQ ratio) and the per-strategy satisfaction table printed to console - a readable check on
Stage 1's raw logs, and the source of the numbers in **Table 7.3**. Read at the level of
independent 95% CIs, Experiment A alone cannot distinguish the RL agent from Random/Static in most
scenarios (the whole point of §7.6), so `paired_diff_experimentA.py` re-computes the comparison
seed-by-seed instead of interval-by-interval, exploiting the fact that seed *i* produces identical
user trajectories across every strategy (§6.3.3-6.3.4). This is what resolves **Table 7.8**.

**Depends on:** Stage 1 (all three main scenarios).

**Generates:**
- Console output only for `run_analysis.py` (the source of Table 7.1-7.3's numbers)
- `output/output-<scenario>/paired_diff_n5.csv`, `paired_diff_n20.csv`,
  `fig3b_paired_diff.png` → **Table 7.8, Figure 7.8**

## Stage 3 - Experiment B: latency/efficiency trade-off (§7.4, RQ2)

```bash
python analysis/analyze_experiment_B.py
```

**Why:** relates CR utilisation ρ = λ_util/C to satisfaction degradation as scenario density
increases (Urban-Light → Urban-Medium → Urban-Dense), for the trained RL agent only. Answers RQ2:
whether the edge-vs-core trade-off is governed by placement quality or by raw capacity.

**Depends on:** Stage 1 (`eval/trained/` logs for all three main scenarios).

**Generates**, in `output/`: `expB_satisfaction_progression.png`, `expB_cr_utilization.png`,
`expB_summary.csv` → **Table 7.5, Figures 7.5-7.6**.

## Stage 4 - Experiment C: mobility and migration (§7.5, RQ3)

```bash
python analysis/analyze_experiment_C.py              # naive: urban_light vs urban_medium
python analysis/analyze_experiment_C_controlled.py    # controlled: urban_medium vs urban_controlled
```

**Why:** the naive comparison (`analyze_experiment_C.py`) contrasts Urban-Light (high mobility, 20
users) against Urban-Medium (low mobility, 30 users) but confounds mobility with load - it cannot
tell whether a change in placement volatility comes from mobility or from user count (§7.5.1,
**Table 7.6**). The controlled follow-up instead compares Urban-Medium against `urban_controlled`,
an identical-topology, identical-load scenario that differs *only* in mobility, isolating the
effect cleanly (§7.5.2, **Table 7.7, Figure 7.7**). Both were run because the first one alone is
not sufficient to answer RQ3 honestly - this is exactly the caveat discussed in §8.3.

**Depends on:** Stage 1, including the separate `urban_controlled` run, for the controlled script.

**Generates**, in `output/`: `expC_satisfaction_comparison.png`, `expC_summary.csv`;
`expC_controlled_satisfaction_comparison.png`, `expC_controlled_placement_volatility.png`,
`expC_controlled_summary.csv`.

## Stage 5 - Experiment D: admission/allocation factorial (§7.7)

```bash
python experiments/generate_results.py --seeds 20 --cr-admission-policy priority --radio-allocation equal_share    # M1
python experiments/generate_results.py --seeds 20 --cr-admission-policy fcfs     --radio-allocation proportional   # M2
python experiments/generate_results.py --seeds 20 --cr-admission-policy priority --radio-allocation proportional   # M3

python analysis/factorial_analysis.py
```

**Why:**
- M0 (`fcfs` + `equal_share`) is the baseline condition and is deliberately *not* re-run here -
  `generate_results.py` refuses to overwrite it.
- M1-M3 retrain both the RN and CR agents from scratch under the other three combinations of two
  binary switches: CR admission order (§5.3.1) and radio-capacity sharing (§3.6).
- The goal is to test whether either modelling choice - rather than the placement algorithm itself
  - explains the RL agent's small deviations from Random/Static found in Stage 2.
- `factorial_analysis.py` then decomposes the four conditions' paired per-seed outcomes into an
  admission effect, an allocation effect, and their interaction (Eq. 6.4-6.6).

**Depends on:** Stage 1 (M0, for the baseline row of every comparison).

**Generates:** `output/output-<scenario>__M{1,2,3}/` (same internal structure as Stage 1's
output), plus `factorial_analysis.csv` at the project root → **Table 7.9-7.11**.

## Stage 6 - Migration-cost models (§5.3.3 / §9.2.2)

```bash
python experiments/compare_migration_cost.py --scenarios urban_medium urban_dense
```

**Why:** the default model treats CR reassignment as instantaneous and free. This script re-runs
*evaluation only* (no retraining - it reuses Stage 1's frozen Q-tables) under two alternative cost
models, `hard_cutover` and `make_before_break`, to check whether penalising placement volatility
changes the picture. Mentioned in the dissertation as verified mechanically but not swept across
the full scenario/seed matrix (§8.4.2) - this script is that mechanical check, not a full
replication of Experiment A under a cost model.

**Depends on:** Stage 1 (`urban_medium`, `urban_dense` models).

**Generates**, in `migration_cost_comparison/`: cached per-run logs under `eval/{scenario}/{mode}/...`
plus `migration_cost_comparison.csv`.

## Stage 7 - Larger-scale robustness (§7.8)

**Urban-N12** (§7.8.2, Table 7.13):

```bash
python experiments/run_large_n12_experiments.py
python experiments/verify_large_n12_models.py
```

**Why:**
- Trains the RN/CR agents from 3 independent seeds under both `fcfs`/`priority` admission
  conditions.
- Evaluates all five strategies over 20 seeds and writes plots + CSVs - a self-contained driver,
  unlike Urban-XL below.
- `verify_large_n12_models.py` sanity-checks the resulting Q-tables (loadable, state counts).

**Depends on:** Stage 0 only (no dependency on Stage 1's models).

**Generates**, under `output/output-urban_large_N12/{fcfs,priority}/`: `models/tseed{0,1,2}/`,
`logs/{train_rn,train_cr}_tseed{0,1,2}/`, `logs/eval/{strategy or rl_tseed{0,1,2}}/s{0..19}/`,
plus `fig_training_curves_tseed0.png`, `fig_strategy_comparison_fcfs.png`,
`paired_diff_rl_vs_baselines_{fcfs,priority}.csv`,
`fig_paired_diff_rl_vs_baselines_fcfs.png`, `paired_diff_priority_vs_fcfs_rl.csv`,
`fig_paired_diff_priority_vs_fcfs_rl.png`, `summary_metrics.csv`.

**Urban-XL** (§7.8.3/§7.8.4, Tables 7.14-7.15):

```bash
python experiments/run_urban_xl_train.py                                # train, skip-if-exists
python experiments/run_urban_xl_eval.py                                 # eval, all baselines + RL (tseed0)
python experiments/run_urban_xl_eval_tseed.py 0                         # RL only, per training seed
python experiments/run_urban_xl_eval_tseed.py 1
python experiments/run_urban_xl_eval_tseed.py 2
```

**Why:**
- `run_urban_xl_train.py` trains the RN/CR agents from 3 independent seeds for both
  `urban_xl_lambda0`/`urban_xl_lambda01` variants (skip-if-exists, same pattern as N12's
  `ensure_train()`).
- `run_urban_xl_eval.py`/`run_urban_xl_eval_tseed.py` then evaluate against those Q-tables, using
  `--track-eval-coverage`/`--dominant-state` (Table 7.15's known/unknown and dominant-state hit
  rates) and `--snapshot-every`/`--state-coverage-every` (Table 7.14's state-coverage and
  policy-snapshot figures).
- Both flag families are backed by `CRPlacementAgent.state_visit_counts` and
  `.capture_policy_snapshot()` in `agents/cr_placement_agent.py`.

**Depends on:** Stage 0 only.

**Generates**, under `output/output-{urban_xl_lambda0,urban_xl_lambda01}/`: `models/tseed{0,1,2}/`,
`logs/{train_rn,train_cr}_tseed{0,1,2}/` (the latter including `cr_state_visit_counts.csv`,
`state_coverage_checkpoints.csv`, `policy_snapshots/*.pkl`), `logs/eval/{strategy or
rl_tseed{0,1,2}}/s{0..19}/` (RL runs including `eval_state_coverage.csv`).

The resulting `results/N12/` and `results/Urban-XL/` folders are committed - see README.md, [Status of this repository](README.md#status-of-this-repository).
